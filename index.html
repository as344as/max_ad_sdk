MAX 广告产品需求

1. 职责与初始化

Android，只使用 AppLovin MAX 聚合。广告 SDK 执行广告能力，Cocos 决定游戏中的请求、展示时机和奖励。

广告请求不以 MAX 初始化完成为前提。请求流程内部自动处理 MAX 初始化及初始化失败后的重试，不等待初始化完成。Cocos 不处理初始化失败，不因此弹 Toast、拒绝请求或关闭激励等待窗；只按广告请求结果处理。初始化回调不额外触发广告请求或自动展示。

远程配置等待仅在每次进程冷启动后检查一次。插屏、激励共用这一轮等待；远程配置返回或 SDK 内部等待结束后，本轮即结束，未返回时使用本地配置。后续进入关卡、回前台、用户点击、失败重试及曝光后预加载均直接使用当前有效配置，不再检查或重启等待时间。迟到的远程配置可更新后续请求使用的配置。等待及回退由 SDK 内部实现，不开放配置参数。

2. 请求与预加载

2.1 共同请求条件

游戏场景请求由 Cocos 发起，曝光后预加载由 SDK 自动发起；两者都由 SDK 检查：广告开关开启、未达每日上限、请求间隔已到、目标 ID 的失败间隔已到且未达当日失败上限。

  • 已有 isReady=true 的广告：SDK 返回 ready，复用，不重复请求。
  • 接受请求后 SDK 立即通知 Cocos「请求中」，等待配置也包含在内。Cocos 等成功、失败或超时回调，不循环发请求。
  • 重复调用时返回同一个 requestId 和当前状态；不新建加载。无可用广告且条件满足，才选择一个 ID 请求。

SDK 在请求结束时回调成功、失败或内部加载超时，具体加载超时由技术内部处理。Cocos 的等待窗取消或超时不算广告 ID 加载失败；已发出的请求仍按自身结果结束，结果迟到也不自动恢复已取消的观看。

2.2 冷启动直接预加载

Cocos 为插屏、激励分别配置 preloadOnColdStart。开启后，每次进程冷启动各检查一次，不要求达到关卡、场景触发间隔或道具数量条件；只加载、不展示。

MAX 尚未初始化完成也可以预加载；SDK 先发起初始化，再继续调用加载，不等初始化完成回调。请求间隔、失败间隔、每日上限、在途请求和已有可用广告仍生效。从后台返回不算冷启动。

"formatPreload": {
  "interstitial": { "preloadOnColdStart": true },
  "rewarded":     { "preloadOnColdStart": true }
}

要每次冷启动都尝试准备两类广告，将上述两项设为 true，并开启 SDK 广告开关、配置各自广告 ID。设为 false 时，冷启动仍可按正常关卡或库存条件检查预加载。

2.3 插屏按关卡请求

Cocos 配置首次展示关卡、展示关卡间隔、提前关卡数。例如第 10 关过关点击下一关展示，提前 2 关请求，则第 8 关开局请求。

  • 首次展示关卡 10、间隔 2：展示节点为 10、12、14……；提前请求从相应节点前 N 关开始，最早第 1 关。
  • 处于第 8～10 关请求范围，进入关卡、到结算页，或回到游戏主界面继续操作时，Cocos 根据 SDK 通知的状态发起一次请求；请求中就等结果。已完成关卡的重玩不产生下一关插屏节点。
  • 点击下一关时无广告：按 Cocos 补请求开关和 SDK 实时补请求开关处理，同时直接进入下一关，不等待、不迟到补弹。
  • 关卡条件和请求间隔需同时满足。冷启动直接预加载另按 2.2 执行。

2.4 激励视频请求

道具有库存时正常使用。用户点击需要看广告的入口，开关关闭、已达每日上限或调用通道明确不可用时，只出 Toast，不出等待弹窗。MAX 尚未初始化、正在初始化或初始化失败，均不构成拒绝理由：开启实时请求且其他条件满足时，照常拉起激励等待弹窗并请求广告，不等初始化完成。

点击时 isReady=true：直接展示激励视频，不出等待弹窗。正在加载时才出等待弹窗等 SDK 结果，不重复请求。无广告也无在途请求时，showFailureToLoad=true 且请求条件满足，才出等待弹窗并请求；否则只出 Toast。激励视频不设展示间隔。

任一道具数量 ≤ 配置阈值 N，可以预加载共享激励广告。冷启动、热启动、消耗道具后及主界面继续操作时检查；多个入口同时满足也只请求一条。预加载不弹等待窗。

无网络且 isReady=false 时只出 Toast。isReady=true 时仍可尝试展示已预加载广告。

2.5 SDK 曝光后预加载

preloadAfterShow 放在 SDK 的 AdConfig 中，插屏、激励分别配置，默认 false。开启后，SDK 收到 MAX 实际展示成功回调（ad_shown）时，立即触发同类型下一条广告的预加载流程，并通知 Cocos，不等待广告关闭。Cocos 不重复请求。

SDK 检查配置、广告开关、每日上限、请求间隔、选中 ID 的失败间隔和当日失败上限；已有可用广告或在途请求则复用。条件不满足就跳过，不启动定时重试。仅调用展示接口或处于 show_pending 不触发；展示前失败或开关关闭也不触发。每个 showId 只触发一次。此机会不依赖 Cocos 的关卡、库存或场景触发间隔，预加载成功不自动展示。

2.6 请求哪个 ID

每类型同一时间只请求一条广告，是否可用由 MAX 判断。每类型可配置多个候选 ID，每次只选一个。

  • 没有有效 eCPM：选配置中 adWeight 权重最高的 ID；同权重时按配置顺序选第一个。
  • 有有效 eCPM：选其对应区间的 ID。有效填充 eCPM 在展示被接受后，用于同类型下次选档。
  • 目标 ID 在失败间隔内或已达当日失败上限：本次不请求，不换其他 ID。

区间连续、不重叠，左闭右开；如 [0,5)、[5,10)，数值 5 属于第二档。例：A 的区间为 [10,1000000)、权重 5，B 的区间为 [5,10)、权重 10；没有有效 eCPM 时选 B。

2.7 请求间隔与失败次数

参数计算口径
loadInterval同类型上次实际加载调用开始计时，无论成功或失败。使用已有广告、等待已有请求不重新计时。
loadFailureInterval同一个广告 ID 最近一次请求失败后等待的秒数；不是累计失败次数。
loadFailureCount同 ID 当日累计请求失败次数上限。成功不清零；达到上限当天不再请求，次日恢复。0 不限。

例：失败间隔 10 秒、每日失败上限 5 次。每次失败后至少等 10 秒，当天第 5 次失败后停止请求该 ID；中间成功过也不清除当天失败次数。

失败次数和每日展示次数按设备本地自然日统计并保存，重启不清零。次日恢复、间隔结束本身都不自动请求；等下一次 Cocos 请求机会或符合开关的实际展示成功机会。

3. 展示与奖励

3.1 展示前判断

插屏、激励每次展示前都调用 isReady，true 才能展示。false 时按 showFailureToLoad 决定是否实时补请求，仍须满足 SDK 请求限制。

仅插屏受 showInterval 限制，从上次实际开始展示起算；关卡或场景条件、展示间隔须同时满足。激励视频不设展示间隔。

两类广告分别配置 showDailyLimit，只累计实际展示。达到本类型每日上限后，停止该类型加载和展示；已有广告也不能展示。0 表示不限。

插屏一次操作最多展示一条。没有可展示广告就继续下一关或关闭失败弹窗；允许补请求时加载留待后续机会，不等待、不补弹。

3.2 激励视频等待弹窗

此处前置条件不包含“MAX 初始化完成”。初始化中且开启实时请求时，仍按下列流程进入等待弹窗，默认最多等待 15 秒。

用户点击激励入口，前置条件通过
├─ isReady=true → 直接展示，不弹等待窗
└─ isReady=false
   ├─ 已在请求中 → 出等待窗，等同一请求的结果
   ├─ 允许实时补请求 → 出等待窗，发起一次请求
   └─ 不允许或被限制 → 只出 Toast

等待中：进度持续推进
├─ SDK 通知 ready → 补满 100% → 展示前再检查 → 展示
└─ SDK 通知失败或等待超时 → 关闭等待窗并提示
  • 进度在最长等待时间内从 0 连续推进到 99%，不提前停在某个百分比；等待动画持续运动。它是等待动画，不表示素材真实下载百分比。
  • 未就绪不显示 100%；广告提前就绪时立即补满并衔接展示，不强制等待动画跑完或额外停留 1 秒。
  • 最长等待默认 15 秒，包含本次可能发生的冷启动配置等待及补请求；到时仍不可用就退出，不停在 99% 无限等。
  • 展示前又变为不可用：允许且条件满足时继续原等待，一次观看最多新发一次实时补请求，不重置超时；否则提示退出。
  • 前三秒隐藏关闭按钮、返回键不关闭；之后允许取消。弹窗期间不穿透点击游戏。
  • 失败、超时或取消后关闭等待窗，按下方规则恢复游戏与倒计时；已取消或已离开的入口不自动展示。下次打开从 0 开始；预加载不弹窗。

Cocos 必须暂停游戏倒计时

激励视频等待弹窗显示期间、激励广告展示期间，关卡倒计时、所有进行中订单倒计时及其他局内玩法倒计时均暂停。这段时间不消耗游戏时间，不触发订单超时或关卡超时失败。暂停实际玩法时钟，不能只停住界面数字。

时机Cocos 行为
即将显示激励等待弹窗同步暂停游戏倒计时，再显示弹窗；不等 SDK 加载结果。
广告已就绪，直接展示调用激励展示接口前先暂停；覆盖 show_pending 到实际展示的交接阶段。
等待窗衔接激励广告保持连续暂停。隐藏等待窗、收到 loaded、show_result 或 reward_earned 都不能提前恢复。
等待取消、超时、加载失败或展示被拒绝结束本次等待／展示流程并解除其遮挡后，尝试恢复；仍在后台或有其他暂停界面时继续暂停。
激励关闭或展示失败收到当前流程的 ad_closed / ad_show_failed，且原生广告遮挡已解除、游戏已回前台后，进入恢复流程；不是回调一到就恢复倒计时。

恢复时只解除本次激励流程带来的暂停；游戏原本处于暂停、失败／复活界面、设置界面或后台时，仍遵循原状态。确实恢复到可操作的关卡后，才从暂停前剩余时间继续，不补扣等待、观看或后台经过的时间。有合法加时／复活奖励时，先应用奖励后的时间，再开始计时；不因广告关闭给所有倒计时重置满格。

同一次等待和观看共用暂停状态，取消与回调按 reward_flow_id／show_id 对应处理；重复关闭或迟到加载不能解除其他流程的暂停。后台预加载、单纯处于 requesting、仅出 Toast 的前置拒绝不暂停游戏。

只暂停玩法时间。激励等待窗的 15 秒上限、前 3 秒关闭限制及动画继续运行；SDK 请求超时、请求／失败间隔、广告可用性检查的素材存放时长照常计时。不能停掉全局时钟导致等待窗永不超时。

3.3 奖励分工

SDK 返回奖励资格与广告关闭结果；奖励资格已取得、广告已关闭、原生遮挡解除且游戏回到前台后，Cocos 按本次入口执行奖励，且只执行一次。恢复流程中先兑现已满足条件的奖励，再按当前游戏状态恢复玩法倒计时；奖励不等待收入上报成功。

道具“+”入口增加库存；“道具开始”入口直接带道具开始游戏；关卡内道具入口执行本次效果。体力、金币、复活、翻倍和重玩按场景表执行，不统一写成“加一个道具”。无奖励关闭、取消或失败不发奖。

不增加第二个广告到账弹窗。

3.4 后台与返回

退到后台不强制关闭正在展示的广告，回到前台不重复展示或发奖。后台不新弹广告；等待弹窗超时继续计时，已取消的流程不恢复。激励等待／观看中的玩法倒计时持续暂停；回前台时若等待窗或广告尚未结束，不能恢复倒计时。

5. 可用性检查与 SDK 通知

以 MAX 的 isReady 判断广告是否可展示，不按加载后固定时长判过期。false 统一称为「不可用」，无需 Cocos 区分是素材失效、未加载还是已消费。

5.1 Cocos 何时检查

定时检查由 Cocos 管理，插屏、激励分别计时；SDK 不自行定时检查。Cocos 调用 getAdState，SDK 当次通过 isReady 判断待展示广告是否可用，并返回 get_state_result。

  • 每次广告填充成功后开始计时，前 50 分钟不做定时检查；满 50 分钟后，仅在游戏前台每 60 秒检查一次。
  • 新广告填充成功后重新计时。复用已有广告、重复成功通知或请求失败不重置计时；按 requestId 区分本次填充。
  • 广告已展示消耗或资源释放后，停止检查该条广告；下一条填充成功再开始。展示中的旧广告结束，不清除下一条广告的计时。
  • 进入后台暂停检查，广告存放时长继续计算；回到前台立即检查一次。尚未满 50 分钟时，后续定时仍从原填充成功满 50 分钟开始。
  • 冷启动清除旧计时，等本次填充成功后重新开始。若重新绑定已有广告，沿用该次填充时间，不以查询时间重新计算。
  • 展示前仍立即检查 isReady，不受定时周期影响。50 分钟是开始检查的时间，不是广告有效期。

5.2 广告不可用时怎么交互

Cocos 定时检查或回到前台 → 调用 getAdState
→ SDK 调用 isReady，返回当前状态
├─ 仍可用 → 保留广告，继续按上述周期检查
├─ 已在请求 → 等原请求结果，不重复请求
└─ 不可用且没有在途请求 → 停止该条广告的定时检查
   ├─ 游戏在后台 → 不补请求
   ├─ 游戏在前台，但不满足预加载条件 → 不补请求
   └─ 游戏在前台，且满足关卡范围或激励预加载条件
      → Cocos 立即尝试补请求，无需等用户操作
      → SDK 检查开关、请求间隔、ID 失败间隔、每日上限和重复请求
      → 通知 requesting → 随后通知 ready / failed / timeout

例：第 8 关开始预加载、第 10 关结束展示。用户停在第 9 关超过 50 分钟，定时检查发现广告不可用，且游戏仍在前台、满足请求条件，就补请求；无需等到结算页。已离开请求范围则不补。激励按道具库存阈值等已有预加载条件判断。

检查失效后的补请求属于 Cocos 预加载，不弹激励等待窗、不自动展示，也不由 showFailureToLoad 控制。若本次补请求受限或失败，等下一次业务机会再判断，不继续每分钟重复请求。用户主动点击展示入口时，仍按 showFailureToLoad 处理实时补请求。

5.3 SDK 给 Cocos 的状态码

以下编号是本广告 SDK 与 Cocos 的交互约定，不是 MAX 原生错误码。统一通过 onAdEvent 回调传递 JSON；立即回执与后续结果使用同一套字段。Cocos 在接入、重新绑定、回到前台及第 5.1 节的定时检查时读取当前状态；已受理请求后等待结果，不重复发起加载。

stateCode 表示当前状态，code 表示这次处理结果。例如请求间隔未到是 code=1005，不是一个新的广告状态。状态码和结果码分别固定，双方不能各自另编编号。

stateCode状态含义Cocos 处理
0not_ready没有可展示广告按当前场景与请求条件决定是否请求；不凭这个状态发奖。
1requesting请求中；仅冷启动首轮可能等待配置等待同一 requestId 的结果，不重复请求；主动观看激励才显示等待弹窗。
2readyisReady=true，可以申请展示用户主动点击激励时直接调用展示；预加载完成不自动展示。
3showingMAX 已回调广告展示成功游戏暂停广告相关操作，等待点击、奖励或关闭通知。
4show_pending已调用展示，等待 MAX 展示结果不再重复调用展示；此时不统计展示成功、不发奖。

5.6 调用与通知顺序

Cocos 调用加载（附 callId、广告类型和当前场景）
→ SDK 请求流程自动处理初始化及失败后的重试，不等待初始化完成
→ SDK 立即回 request_result
  ├─ code=0，stateCode=1 → 等待同一 requestId 的 load_result
  ├─ code=0，stateCode=2 → 已有广告；有效的主动观看可直接调用展示
  └─ code≠0 → 按原因提示或继续游戏，不循环重试

Cocos 调用展示（附新的 callId 和实际展示场景）
→ SDK 检查展示条件和 isReady
  ├─ 可展示 → show_result：code=0，stateCode=4
  │          → ad_shown → reward_earned（仅激励）/ ad_clicked / ad_closed
  ├─ 已调用后失败 → ad_show_failed：code=2003
  └─ 不可展示 → show_result：对应原因码

展示时无广告：已有请求则返回 code=1009、stateCode=1 和原 requestId；无请求但允许实时补请求且条件满足，也返回 code=1009、stateCode=1 和新 requestId，随后回 load_result。关闭实时补请求且无在途请求时返回 code=1009、stateCode=0；被间隔或上限限制时返回对应原因码。

激励只有当前观看仍有效时才等结果并展示；已有广告直接展示，不出等待窗。Cocos 等待弹窗最多 15 秒，取消或超时不取消、重置 SDK 的在途请求，也不产生 SDK 加载超时代码；迟到结果可更新广告状态，但不能恢复已取消的观看。插屏无广告时直接继续游戏，补请求结果不迟到补弹。

已受理请求必须给一次最终 load_result。底层加载超时由技术内部处理，不开放产品参数。SDK 超时后广告又变为可用，可发送 state_changed，但不能再给同一请求第二次最终结果。

曝光后由 SDK 自动预加载：MAX 回调实际展示成功 → SDK 通知 ad_shown → 检查本类型 preloadAfterShow → 立即触发下一条同类型广告的预加载，不等 ad_closed。每个 showId 只触发一次；Cocos 不开等待弹窗、不重复 requestAd，也不自动展示下一条。

新请求受理后发送 state_changed（loadStateCode=1），结束后发送 load_result（loadStateCode=2 表示就绪，失败为 0）。两者沿用新 requestId，callId=null、triggerType=after_show，并带 sourceShowId。受限跳过时不伪造请求中或加载结果；已有下一条广告或在途请求则复用。

当前广告仍在展示时，stateCode 保持 3，下一条广告的进度使用 loadStateCode；预加载成功不能把当前展示提前标记为结束。广告关闭后不再触发预加载：根据下一条广告情况，状态转为 ready、requesting 或 not_ready。奖励仍只按原 showId 的奖励资格和关闭回调处理。

7. 埋点与收入

事件与收入由技术统一上报，不在广告配置中增加上报开关、渠道和事件映射参数。Cocos 传入当前场景上下文。

7.1 ad_show 和 ad_impression 的区别

ad_show 看“广告是否真的展示成功”；ad_impression 看“这一条曝光带来多少收入”。本版 ad_show 在 MAX 展示成功回调时记录；Firebase 标准 ad_impression 在 MAX 收入回调时带金额记录。调用展示接口、填充成功和准备进度 100% 都不算展示成功。

同一次广告可以有这两个不同用途的事件，但不能相加算两次曝光。展示次数按唯一 show_id 统计，收入按每条广告的收入记录去重；Firebase 不额外发送一条没有收入的同名 ad_impression。参见 Firebase 的 MAX 收入上报说明。

7.4 24 小时曝光 LTV

sdkConfig.common.ltv24Code 和 ltv24Range 各用 - 分组并一一对应。每组为 LTV美元、曝光次数、平均eCPM美元；0 忽略该条件，非零条件全部满足才触发一次。组数须一致、编码不重复、条件不能全为 0。

ltv24Code 填 Adjust 的真实事件 token。平均 eCPM = 累计广告收入 ÷ 曝光次数 × 1000；无曝光不计算。例：0.05,4,10 表示首开 24 小时内 LTV ≥ 0.05 美元、曝光次数 ≥ 4、平均 eCPM ≥ 10 美元。每个点位只触发一次，重启不重复。

首版压力快照：关卡或订单剩余时间首次 ≤20 秒、连续 15 秒有效游戏时间未消除、空位从大于 0 变为 0；同一局／订单每种条件只记录一次。订单出现与进入失败另记。20／15 秒仅为分析采样口径，不改变玩法或广告请求条件；后续调整递增 analysis_version。

8.5 第一版的三张分析表

以下时间窗口是首版统一统计口径，不是已测出的最佳阈值。数量按指定唯一 ID 去重；未到观察截止、迟到结果和未知结果单列，不能直接算失败或不选择。预加载、SDK 限制和等待超时遵循前文规则，本章不新增请求机会。

分析表一行是什么／怎么分组核心口径能据此做什么
插屏打扰表一条 interstitial_opportunity；按 scene_id、胜败、失败次数、之前广告负担、有效游戏间隔、实验组分组展示率：实际 ad_show 的机会数 / 全部场景机会数。恢复率：展示后 5 分钟内游戏恢复的 show 数 / 全部实际 show 数。继续开局率：机会后 10 分钟内有新 level_start 的机会数 / 全部机会数；保留未展示机会与跳过原因识别失败关闭、激励后插屏等风险组合；描述性结果不直接当因果结论
道具选择表一份 gameplay_checkpoint 或点击前快照；按关卡版本、局面、道具解锁／库存／成本分组；主动点击快照与压力采样快照分表道具选择率：观察窗口内首个 tool_click 选择该道具的快照数 / 该道具可见、解锁且可操作的快照数。另拆库存／金币／广告途径、未选择、离开和观察不足区分真正的局面需求与库存、解锁、价格、引导造成的选择；多道具共现时不能只按点击总数排名
激励交换表一条可见 offer 及其观看流程；按需求类别、scene_id、承诺奖励、局面、广告负担分组观看选择率：发生 reward_offer_click 的 offer 数 / 可见 offer 数。播放率：有 ad_show 的 flow 数 / 全部选择观看 flow 数。兑现率：最终 reward_completed 的 show 数 / 已获 ad_reward_earned 的 show 数；配合等待耗时和终止原因分清不想看、想看但没播、看完没兑现，以及兑现后短时间再次求助

激励漏斗观察窗口：offer 从实际可见到隐藏／离开该页面为一次，点击只关联当时的 offer；按入口是否可用分组，仍保留不可用入口的曝光，不把“无广告”过滤掉。观看流程按点击后 24 小时窗口统计播放与终止结果，未到窗口截止的流程不混入成熟样本；尚未恢复／未结算单列，不推断为用户拒绝。

道具选择观察窗口：压力快照后最多 10 秒有效游戏时间；首个 tool_click、下一压力快照、该订单结束或本局结束先到则截止。每次点击只分配给最近一份仍有效的压力快照。同帧多条件合并到一个 snapshot_id；没有点击且有效观察满 10 秒才记 no_choice，提前离开记 left，数据中断记 unknown。点击前快照只描述使用者，不用于估计未使用者比例。

收益兑现之后：即时道具／复活分别统计同局后续 60 秒有效游戏时间内的再次失败和再次求助，取首次相关结果；通关作为独立结果，观察不足单列。领取库存则在领取后 24 小时跟踪准确关联的消耗；无法追溯库存批次时，只能报“领取后发生过该道具使用”，不能声称使用了该条广告发的道具。资源整体流向看 resource_change。

奖励结算：ad_reward_earned 与 ad_closed 先后顺序不限，按原奖励规则兑现。样本先标 pending，等待回到游戏或下次恢复后的幂等结算；报表对发生满 24 小时的奖励资格统计兑现率，并单列仍未恢复／未结算比例，不能一律判定发奖故障。

8.6 优先验证的两个实验

优先级只改变什么主要结果与保护指标
1：失败关闭插屏稳定用户分组：按现配置展示 vs. 跳过 failure_close_interstitial；其余关卡、奖励和频控保持一致主要结果：入组后 7 日广告收入 / 全部分组用户。保护指标：入组后 24–48 小时返回游戏比例、7 日人均实际开局数
2：激励之后的插屏第一个实验结束后单独做；按“距最近激励后的有效游戏时间”设置一档插屏保护，候选阈值先看间隔分布再定同一组主要结果与保护指标；另看触发保护的比例、被跳过的插屏和激励观看是否变化

在用户首次到达相关机会、进行实验抑制前完成分组；后续保持同组。收入包含两种广告，按曝光发生时间归入入组后 [0,168 小时)，不以收入回调到达时间移动归属。只比较观察窗口完整的同批用户，包含未展示广告者；报告样本量、差值及不确定范围，不按单日涨跌提前挑赢家。没有真实基线前，不给耐受度、收入或留存编造达标值。

暂停游戏、广告外跳、网络断开、界面恢复异常要分开看；没有后续事件只能说明未观察到继续行为。会话内重复机会用于定位场景，实验结论按用户汇总，避免把广告多的重度用户当作多个独立样本。
